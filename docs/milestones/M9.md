# Part 1 — Milestone Overview

## Production goal

At the end of M9, any logged-in ops user (CO, CHO, admin) can download CSV files of the operational data they can already see on screen:

1. Per-school children roster, volunteer roster and weekly timetable, from the matching School detail tabs
2. A schools summary, plus combined children and volunteer lists across every school in their scope, from the Schools list page
3. An **ops gap report** that lists missing setup work (children without buckets, slot-classes without volunteers, and so on) across their schools
4. Every export is recorded in an audit log (who, what, filters, row count, when)

Exports open cleanly in Excel and Google Sheets, including names in Hindi and regional languages.

## What does NOT ship in M9

Hard out-of-scope. Don't build any of these in M9.

- **Excel (.xlsx) or PDF output.** CSV only.
- **Scheduled or emailed exports.** Celery is not active (see project notes); all exports are synchronous downloads.
- **Background or async export jobs.** Data volumes (hundreds of schools, low thousands of children) fit in a single synchronous request.
- **Past academic years.** Exports cover the active academic year only (R8). A year picker is deferred until year progression (M5) ships.
- **Custom column pickers or saved export templates.**
- **Import / bulk upload from CSV.**
- **Attendance, session-level or mentoring-circle reports.** Those models don't exist yet.
- **Admin UI for viewing the export audit log.** Rows go to the DB and are queried directly for now.
- **Sync log / realtime event exports.** The admin tabs already have filters; not an ops need.
- **Removal-reason analytics by category.** Reasons are exported as stored (see `DECISIONS.md` on free-text reasons).

> If something here turns out to be unexpectedly needed for M9, talk to the human first before adding scope.

## Key architectural decisions for M9

**1. The server generates the CSV.** The backend builds every file. The frontend only triggers the download. This keeps business logic out of the frontend (frontend `CLAUDE.md`) and is the only way to support cross-school exports without paging through many endpoints.

**2. Export access follows view scope.** Anyone who can view a school can export it (R13). Per-school exports guard with `get_school_or_403`. Cross-school exports start from `schools_visible_to(user)`. There is no separate export permission. Because `_classify` counts CXO as an admin, CXO sees all schools, the same as on the Schools page.

**3. Personal data is included and every export is audited.** Child date of birth and volunteer contact numbers are included. Every successful export writes one `ExportLog` row. This is recorded in `DECISIONS.md` D031.

**4. Active academic year only.** All year-bound data (sections, slots, school volunteers, term dates) is filtered to the globally active year. If no year is active, the endpoint returns 404 via the existing `get_active_academic_year()` ("No active academic year is configured.").

**5. Exports reuse the existing read services.** Children exports build on `services/children/queries.py::list_children` (it already adds class and section names). Volunteer exports use the same PartnerWorknode → User matching as `services/volunteers/list.py`. Timetable exports use `services/slot_classes/schedule.py::get_school_schedule`. The schools summary uses `services/schools/queries.py::get_school_stats`. Counts in a CSV must match the counts on screen.

**6. Built in memory, not streamed (v1).** Rows are built as a list (services still use bulk queries and `.iterator()`), the audit row is written with the real row count, then a plain `HttpResponse` is returned. Streaming would push the audit write into the generator after the view returns, where it is silently lost on client disconnect and runs outside request error handling. The largest export is ~1 MB. Switching to streaming later only touches `csv_writer.py`.

**7. Excel-safe output.**
- UTF-8 with a BOM, CRLF line endings, and a header row always present (even when there are 0 rows).
- Any cell starting with `=`, `+`, `-`, `@`, tab or carriage return gets a leading `'` to prevent formula injection.
- Dates are ISO `YYYY-MM-DD`; times are `HH:MM`.
- Multi-value cells are joined with `; `.

**8. Filenames are deterministic.**
- Per school: `{export}_{partner_id}_{YYYY-MM-DD}.csv`.
- Cross-school: `{export}_all_{YYYY-MM-DD}.csv`.
- Sent via `Content-Disposition`, which the frontend reads.

**9. The export matches what is on screen.** Per-school children exports pass all of the Children tab's filters: search, class, bucket or unassigned, and status (changed 2026-09-27; originally status only). Cross-school exports pass the Schools page search text. Exports use their own search, `services/exports/scope.py::filter_schools_like_page`. It matches **name, city or CO name**, the same fields the page filters on in the browser. Blank-after-trim means no filter; otherwise the raw text is matched, as the page does. `GET /api/schools/?search=` keeps its M1 behaviour (name, city or state, TC-M1-4-06). Decided 2026-09-27; see `plans/F-M9-5-plan.md`.

## F-M9-1 — Export foundation

### What it does

Adds the shared pieces every export uses: a CSV response builder, an audit log table, a router, and a reusable frontend button. It doesn't produce any user-visible export by itself.

**Who uses it:** Developers (infrastructure for F-M9-2..8).

### Schema — models and migrations

```python
# sessionops/models/export_log.py
EXPORT_TYPES = [
    ("school_children", "School children roster"),
    ("school_volunteers", "School volunteer roster"),
    ("school_timetable", "School timetable"),
    ("schools_summary", "Schools summary"),
    ("all_children", "All children in scope"),
    ("all_volunteers", "All volunteers in scope"),
    ("gap_report", "Ops gap report"),
]

class ExportLog(models.Model):
    export_log_id = models.BigAutoField(primary_key=True)
    user_id = models.ForeignKey("sessionops.User", on_delete=models.PROTECT,
                                db_column="user_id", related_name="+")
    export_type = models.CharField(max_length=40, choices=EXPORT_TYPES, db_index=True)
    school_id = models.BigIntegerField(null=True, blank=True, db_index=True)  # loose FK to partner.partner_id; null = cross-school
    filters = models.JSONField(default=dict)      # e.g. {"status": "all"} or {"search": "pune"}
    school_count = models.IntegerField(default=1)  # schools covered by the export
    row_count = models.IntegerField()
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        db_table = "export_log"
        indexes = [models.Index(fields=["user_id", "created_at"])]
```

The log is append-only. It has no soft-delete fields, because rows are never edited or removed; this is an explicit exception to R9's column set, the same as the sync logs (confirmed 2026-09-27).

### Backend scope

- `services/exports/csv_writer.py`
  - `build_csv_response(filename, header, rows)` returns an `HttpResponse` (`text/csv; charset=utf-8`, `Cache-Control: no-store`) with a BOM and CRLF line endings.
  - Every cell goes through `_safe_cell()`, which handles formula-injection escaping and formats None, dates and times.
- `services/exports/audit.py` — `log_export(user, export_type, *, school_id=None, filters, school_count, row_count)`.
- `services/exports/scope.py`
  - `export_school_ids(user, search)` returns partner ids from `schools_visible_to(user)`, filtered by the same name/city/state search as `list_schools`.
  - Active year comes from the existing `services/academic_year/queries.py::get_active_academic_year()` (raises `NotFound`, 404).
- `api/exports_api.py` — the router, mounted in `routes.py`. Per-school routes go under the existing `/api/schools/` prefix; cross-school routes go under `/api/exports/`.

### Frontend scope

- `lib/api/client.ts` — update `download()`:
  - Use the filename from `Content-Disposition` when present, with the passed filename as fallback.
  - Revoke the object URL after the click (use `setTimeout`).
  - On an error response, parse the blob as JSON and throw the normal API error so toasts show `detail`.
- `lib/api/services/exports.service.ts` — one typed function per export.
- `components/common/ExportButton.tsx`:
  - An outlined MUI button with a download icon. A single option renders as a button; several options render as a menu.
  - Shows a spinner while downloading and disables itself to prevent double clicks.
  - Shows an error toast on failure.

### Acceptance criteria

- [ ] `export_log` migration applies cleanly on a fresh DB, and `test_model_column_conventions.py` passes
- [ ] `build_csv_response` output begins with a UTF-8 BOM and has a header row even with 0 data rows
- [ ] Cells `=SUM(A1)`, `+91…`, `-5`, `@x` are written with a leading `'`
- [ ] `None` → empty cell; `date` → `YYYY-MM-DD`; `time` → `HH:MM`
- [ ] Exactly one `ExportLog` row per completed export, with the correct `row_count`
- [ ] An export request with no active academic year → 404 with a readable message
- [ ] Unauthenticated request → 401
- [ ] `ExportButton` shows a spinner while downloading, blocks double clicks, and shows the backend `detail` in a toast on error

### Test scenarios

- Happy path: build 3 rows → correct CSV bytes, one log row with row_count=3
- Edge case: 0 rows → header only, log row with row_count=0
- Edge case: a Devanagari name round-trips unchanged
- Error case: no active year → 404, no log row

## F-M9-2 — School children roster export

### What it does

Downloads the children of one school as a CSV from the Children tab: exactly what the tab shows. It applies the tab's current search, class, bucket (or "unassigned") and status filters. It still requires an active academic year (404 otherwise), and `age` is the stored value the tab shows, not recalculated from date of birth.

**Who uses it:** CO, CHO and admin, for any school they can view.

**Business rules enforced:**
- R13: scope via `get_school_or_403`
- R9: children with `removed=True` are never exported
- R10: inactive children include their latest active removal reason and details

### Columns

`child_id, first_name, last_name, gender, date_of_birth, age, class, bucket, status, date_of_enrollment, mad_joining_date, mother_tongue, city, removed_reason, removal_details, removed_on`

- `class` = `current_class_name`; `bucket` = `current_section_display_name`, falling back to `current_section_name`. Both come from `list_children`.
- `status` is `active` or `inactive`.
- The removal columns are filled only for inactive children, from their latest `ChildRemovalLog`. `removed_reason` uses the choice display label.
- Rows are sorted by class, then bucket, then first name (children with no class or bucket come last).

### Backend scope

- Endpoint: `GET /api/schools/{school_id}/exports/children.csv?status=active|inactive|all&search=&class_id=&section_id=&unassigned=` (status defaults to `all`)
- Service: `services/exports/children.py::school_children_rows(school_id, *, status, search, class_id, section_id, unassigned)`. It passes the filters straight to `list_children` and adds removal-log subqueries.

### Frontend scope

- `ChildrenTab.tsx`: an `ExportButton` in the page header, next to Enroll Child, that passes all current filters. It is shown regardless of `canModify`.

### Acceptance criteria

- [ ] The row count equals the tab's "N results" count for the same filters
- [ ] `status=active` excludes inactive children; `inactive` includes only them; `all` includes both
- [ ] `removed=True` children never appear
- [ ] A child with no class or bucket assignment has empty class and bucket cells (not "None")
- [ ] An inactive child shows the removal reason label and date
- [ ] A CO requesting another CO's school gets 403 and no log row
- [ ] Search, class, bucket and unassigned filters narrow the rows exactly as they do on the tab
- [ ] The log row has `export_type=school_children`, `school_id`, and `filters` containing only the non-empty values

### Test scenarios

- Happy path: 3 active + 1 inactive child, `status=all` → 4 rows, inactive row has reason
- Edge case: a child assigned to a class but not a bucket → bucket cell empty
- Error case: out-of-scope school → 403

## F-M9-3 — School volunteer roster export

### What it does

Downloads the volunteers of one school with their current slot-class assignments, from the Volunteers tab.

**Who uses it:** CO, CHO and admin, in scope.

**Business rules enforced:**
- R13: scope via `get_school_or_403`
- R4/R6: each volunteer shows only their active slot-class assignments in this school and the active year
- Volunteer matching is the same as the Volunteers tab (PartnerWorknode → `User.worknode_id`, active users only)

### Columns

`user_id, name, email, contact, role, city, slot_class_count, assignments`

- `assignments` lists entries like `Mon 10:00-11:00 · Class 5 · 5A · English`, joined with `; `.

### Backend scope

- Endpoint: `GET /api/schools/{school_id}/exports/volunteers.csv`
- Service: `services/exports/volunteers.py::school_volunteer_rows(school_id)`
  - Reuses the user lookup from `list_school_volunteers`.
  - Loads active `SlotClassSectionVolunteer` rows for those users in this school and year in one query (`select_related` slot, section, subject), then groups them in Python.

### Frontend scope

- `VolunteerListTab.tsx`: an `ExportButton` in the tab header.

### Acceptance criteria

- [ ] The row count equals the number of volunteers on the Volunteers tab
- [ ] A volunteer with 2 active slot-classes shows `slot_class_count=2` and both entries
- [ ] Soft-deleted assignments and slots from other years are not listed
- [ ] Inactive users are excluded
- [ ] Out-of-scope school → 403

### Test scenarios

- Edge case: an assignment whose slot was deleted → not listed
- Error case: out-of-scope school → 403

  - There is no per-school query loop.

### Frontend scope

- `SchoolToolbar.tsx`: an "Export" `ExportButton` menu. Its first item is "Schools summary". It passes the current search text.

### Acceptance criteria

- [ ] The row set equals the schools the user sees on the Schools page for the same search
- [ ] `active_children` and `volunteers` equal the Schools list values for each school
- [ ] A school with no term dates has empty term cells
- [ ] A CO sees only their schools; a CHO only their worknode schools; an admin all
- [ ] The query count doesn't grow with the number of schools (assert with `django_assert_max_num_queries`)
- [ ] The log row has `school_id=null`, `school_count` and `filters={"search": ...}`

### Test scenarios

- Edge case: a search term matching 1 school → 1 row

## F-M9-8 — Ops gap report

### What it does

Downloads a to-do list of incomplete setup across the user's schools. There is one row per gap, so ops can sort and filter by school or gap type.

**Who uses it:** CO, CHO and admin. It is used for weekly setup follow-up.

### Gap types

| gap_type | Detected when | entity / detail |
|---|---|---|
| `SCHOOL_NO_TERM_DATES` | No active `SchoolSessionDetails` for the active year | — |
| `SCHOOL_NO_SLOTS` | No active slots for the active year | — |
| `CHILD_NO_BUCKET` | Active child with no active `ChildClassSection` | child id + name / class name |
| `SLOT_CLASS_NO_VOLUNTEER` | Active slot-class with 0 active volunteers | slot-class id / "Mon 10:00 · 5A · English" |
| `VOLUNTEER_UNASSIGNED` | Volunteer matched to the school with 0 active slot-classes there | user id + name / contact |

### Columns

`school_id, school_name, school_city, co_name, gap_type, entity_id, entity_name, detail`

Rows are sorted by school name, then gap type.

### Backend scope

- Endpoint: `GET /api/exports/gaps.csv?search=`
- Service: `services/exports/gaps.py::gap_rows(partner_ids)`, with one bulk query per gap type.

### Frontend scope

- `SchoolToolbar.tsx` Export menu → "Gap report".

### Acceptance criteria

- [ ] Each gap type is detected for a school that has it and not reported for one that doesn't
- [ ] A fully set-up school produces no rows
- [ ] The `CHILD_NO_BUCKET` count equals the Children tab's "unassigned" filter count
- [ ] Only in-scope schools appear

### Test scenarios

- Happy path: one school seeded with each gap → 5 rows, one per type
- Edge case: a fully set-up school → header only
- Scope: out-of-scope gaps are not included
