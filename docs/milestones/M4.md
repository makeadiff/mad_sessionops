# Part 1 — Milestone Overview

## Production goal

At the end of M4, the Session-Ops platform has two complete pieces of infrastructure:

1. **A calendar foundation.** Each school's Calendar tab is active. CO/admin/CHO can configure the academic session boundary (one-time set) and add per-school holidays within that window. Calendar tab renders a month grid showing session window styling and holiday pills.
2. **An incremental, observable, controllable Hasura sync.** The 6-hour blanket sync from M1 is replaced by 6 incremental runs per day (aligned to the upstream data pipeline schedule). Admins have a dedicated dashboard to view sync history, trigger manual syncs, re-sync a single user by login, and see notifications for sync failures or silence.

The Calendar tab and the admin sync dashboard are both new entry points. The calendar block is pivot-independent and unaffected by the future M6 bucket pivot. The sync block extends M1's foundation — M3's worknode_id and partner_worknode population continue to work after M4 ships.

## What does NOT ship in M4

Hard out-of-scope. Don't build any of these in M4 even if asked.

- **Holiday impact on slot-classes.** Holidays are display-only in M4. Slot-classes continue to run on every matching day_of_week; the system does not auto-suppress holiday dates. The deeper "session occurrence" model arrives later (M5+).
- **Multi-session per academic year.** One active session per (school, academic_year). Multi-term (Term 1 / Term 2) is out of scope.
- **Session edit and delete.** Session is **one-time-only**. Once configured, no edit, no delete in M4. Mistakes require admin DB intervention.
- **Year progression / session archival.** Session rows are designed to support `is_active=false, removed=false` archival when M5 ships year progression, but M4 does not handle the transition itself.
- **Webhook receiver from Hasura.** Parked outside the milestone plan. M4 stays on cron.
- **Celery + Redis.** Dropped from scope.
- **Hard-delete handling in sync.** If a record disappears from Hasura, it stays in Session-Ops untouched. Deletion handling deferred to M5+.
- **Configurable alert thresholds.** N=3 consecutive failures and M=24h silence are hardcoded for M4.
- **Email/Sentry alert channels.** Alerts are application-level (in-app notifications) only. Email and Sentry integration deferred.
- **Force-full re-sync from the UI.** Manual "Sync now" runs incremental only. Force-full is implicit on first run after deploy (when cursors are null).
- **CO/CHO access to sync admin dashboard.** Admin-only.
- **Holiday categories beyond the three reasons.** Hardcoded enum: `mad_event`, `holidays`, `cancelled_from_school_end`.
- **Slot teaching day highlighting on calendar.** Layer 3 of the calendar (highlighting Mondays when school has a Monday slot) is deferred.

> If something here turns out to be unexpectedly needed for M4, talk to the human first before adding scope.

## Key architectural decisions for M4

These are foundational. Read before designing models or services.

**1. Two separate domains.** The calendar block (F-M4-1 through F-M4-3) and the sync block (F-M4-4 through F-M4-8) share no entities. Build order has calendar first because it's simpler and frontend-heavy; sync second because it touches infrastructure.

**2. Session is one-time, immutable.** Once a CO saves the session start_date and end_date, those values cannot be edited in M4. The set-session modal shows a prominent warning. If the wrong dates were entered, recovery is admin DB intervention. Future milestones may add an admin "reset session" capability.

**3. Session defaults come from Partner.** Pre-fill the set-session modal with `start_date = mou_sign_date + 60 days` and `end_date = mou_end_date`. CO can override before saving. If `mou_sign_date + 60 days` is in the past, show the value as-is — CO sees and decides.

**4. Holidays are gated behind session.** No "Add Holiday" affordance shown until the session is configured. Calendar tab empty state shows "Configure session" CTA prominently.

**5. Per-school holiday model.** Each school maintains its own holiday list. No global / shared / cascading holiday model. Holidays are date ranges (single-day = start == end). Holiday rows must fall within the active session's start_date and end_date.

**6. Holiday overlap blocked.** Within a school, holidays cannot overlap with other active holidays. CO must remove an existing overlapping holiday before adding a new one.

**7. Holiday date edit = soft-delete + create new.** If CO edits the start_date or end_date of a holiday, the existing row is soft-deleted and a new row is created. Other fields (reason, description, remarks) edit in place. This preserves audit history of date changes.

**8. Calendar tab is month grid only in M4.** Default view is month grid. Week view and list view are deferred.

**9. Year progression archives session rows.** When year progression runs (M5), the old session row becomes `is_active=false, removed=false`. A new session row is created for the new academic year. M4 schema supports this — `school_session_details` has both flags.

**10. Per-entity cursor for incremental sync.** Each entity (user, partner) tracks its own cursor: the max `updated_datetime` from Hasura seen so far. Next sync run passes that as the `updated_after` parameter. Failures in one entity don't reset the cursor for the others.

**11. `partner_worknode` is full-sync.** Hasura has no incremental endpoint for `partner_worknode`, and the table volume is small. M4 sync fetches all `partner_worknode` rows on every run and upserts. No cursor for this entity.

**12. First run after deploy is full sync.** When entity cursor is null (post-deploy or after a reset), the first sync run for that entity fetches all records and sets the cursor to the max `updated_datetime` seen. Subsequent runs are incremental.

**13. Six runs per day on the cron, aligned to upstream pipeline.** Cron times: 8 AM, 10 AM, 12 PM, 2 PM, 4 PM, 6 PM Asia/Kolkata. Each scheduled 1 hour after the corresponding upstream data pipeline run (7/9/11/13/15/17 + 1 hour) so the data is fresh when sync hits Hasura.

**14. No deletion handling in M4.** If a record disappears from Hasura, it remains in Session-Ops as it was last seen. Future milestone may add reconciliation.

**15. SyncRun is the central audit log for all sync activity.** Schema extended in M4 to include `sync_type` (auto/manual/manual_single_user), `entity_type` (user/partner/partner_worknode), `updated_after` cursor passed, `target_identifier` (for single-user sync), `running` status. Existing M1 fields preserved.

**16. Concurrent sync runs blocked.** If a SyncRun is in `running` status, new manual triggers are blocked with a graceful message. Cron also respects this — if a previous run hasn't completed, the new cron run is skipped and a notification is generated.

**17. Application-level notifications only.** Sync failures and silence trigger in-app notifications via a new `notification` table. No email, no Sentry, no external integrations in M4. The notification system is per-user (one row per admin per event). Recovery from a failure shows on the dashboard but does not generate a notification.

**18. Cron health is inferred from SyncRun history.** Admin dashboard shows a "cron healthy" indicator based on whether the most recent successful sync is within the expected cadence (≤ 2 hours given the 2-hour run interval). No direct crontab inspection from Django.

**19. Admin-only access to all M4 sync infrastructure.** CO and CHO have no visibility into sync state, dashboards, or notifications. The notification bell in the header is only visible to admins.

**20. Admin page lives at a separate URL with a tab structure.** Accessed via header profile menu → "Admin" link → `/admin` page. First tab is "Data Sync." Layout mirrors school detail page (left tab nav, right content). Navigation back to home/schools is available in the header.

- `GET https://hasura.makeadiff.in/api/rest/partner_data` — incremental partner sync (param: `updated_after`)
- `GET https://hasura.makeadiff.in/api/rest/user/by-login` — single user fetch (param: `user_login`)

```

```

The second line is the heartbeat cron that fires the "sync silent" notification check hourly.

```python
@transaction.atomic
def create_school_session(school_id, payload, user):
    if not can_user_modify_school(user, school_id):
        raise PermissionDenied()

    # Validate dates
    if payload["start_date"] >= payload["end_date"]:
        raise ValidationError("session start_date must be before end_date")

    # Get the active academic year
    say = get_active_school_academic_year(school_id, user)

    # Check: no active session already exists for this (school, academic_year)
    existing = SchoolSessionDetails.objects.filter(
        school_id=school_id,
        school_academic_year_id=say,
        is_active=True,
        removed=False,
    ).first()

    if existing:
        raise ConflictError(
            "Session already configured for this academic year. "
            "Session is immutable in M4."
        )

    return SchoolSessionDetails.objects.create(
        school_id=school_id,
        school_academic_year_id=say,
        start_date=payload["start_date"],
        end_date=payload["end_date"],
        created_by=user,
    )
```

### Backend — services

#### `services/holidays/create.py::create_holiday`

```python
@transaction.atomic
def create_holiday(school_id, payload, user):
    if not can_user_modify_school(user, school_id):
        raise PermissionDenied()

    # Session must be configured
    session = SchoolSessionDetails.objects.filter(
        school_id=school_id,
        is_active=True, removed=False,
    ).first()

    if not session:
        raise ValidationError(
            "Academic session is not configured. Configure the session before adding holidays."
        )

    # Validate dates
    start = payload["start_date"]
    end = payload["end_date"]

    if start > end:
        raise ValidationError("start_date must be on or before end_date")

    # R-cal-2: holiday must fall within session window
    if start < session.start_date or end > session.end_date:
        raise ValidationError(
            f"Holiday must fall within the session window "
            f"({session.start_date} – {session.end_date})."
        )

    # R-cal-3: no overlap with other active holidays at this school
    overlap = SchoolHoliday.objects.filter(
        school_id=school_id,
        is_active=True, removed=False,
    ).filter(
        Q(start_date__lte=end) & Q(end_date__gte=start)
    ).first()

    if overlap:
        raise ConflictError(
            f"This holiday overlaps with existing holiday "
            f"({overlap.start_date} – {overlap.end_date}, "
            f"'{overlap.get_holiday_reason_display()}'). Remove it first."
        )

    return SchoolHoliday.objects.create(
        school_id=school_id,
        holiday_reason=payload["holiday_reason"],
        start_date=start,
        end_date=end,
        holiday_description=payload.get("holiday_description"),
        remarks=payload.get("remarks"),
        created_by=user,
```

### What it does

```python
@transaction.atomic
def sync_user_by_login(user_login, triggered_by_user):
    if not triggered_by_user.is_admin:
        raise PermissionDenied()

    # Check no other sync is running
    running = SyncRun.objects.filter(status="running").exists()
    if running:
        raise ConflictError("Another sync is already in progress. Please wait.")

    run = SyncRun.objects.create(
        sync_type="manual_single_user",
        entity_type="user",
        target_identifier=user_login,
        status="running",
        triggered_by=triggered_by_user,
    )

    try:
        from sessionops.services.hasura.client import fetch_user_by_login
        user_data = fetch_user_by_login(user_login)

        if not user_data:
            run.status = "failed"
            run.error_details = f"No user found with login {user_login} in Hasura"
            run.completed_at = timezone.now()
            run.save()
            raise NotFound(run.error_details)

        # Upsert user using existing M1 logic
        upserted = upsert_user_from_hasura(user_data)

        run.status = "success"
        run.records_fetched = 1
        run.user_logins = [{"user_login": upserted.user_login, "user_name": upserted.user_name}]
        run.completed_at = timezone.now()
        run.save()

        return upserted
    except Exception as e:
        run.status = "failed"
        run.error_details = str(e)
        run.completed_at = timezone.now()
        run.save()
        raise
```

## F-M4-6 — Paginated incremental sync

### What it does

The keystone of the sync block. Replaces the M1 blanket sync (`run_sync()`) with a per-entity incremental sync that uses each entity's `updated_datetime` as the cursor.

Each sync run cycle (cron-triggered or manual):
1. Get current cursor for `user` (max `User.updated_datetime` in DB)
2. Fetch Hasura users with `updated_after = current_cursor`
3. Upsert each user; advance cursor based on new max
4. Create SyncRun row with status, records, errors
5. Repeat for `partner` (same pattern)
6. Repeat for `partner_worknode` — **full-sync**, no cursor

If any entity's sync fails, the others continue. Each entity has an independent SyncRun row.

### Backend — services

#### `services/sync/incremental.py::run_incremental_sync`

```python
@transaction.atomic
def run_incremental_sync(sync_type="auto", triggered_by=None):
    """Top-level orchestrator. Returns dict of {entity_type: SyncRun}."""

    # Check no other sync is running (across all entities)
    running = SyncRun.objects.filter(status="running").exists()
    if running and sync_type == "manual":
        raise ConflictError("Another sync is already in progress.")

    results = {}

    for entity_type in ("user", "partner", "partner_worknode"):
        try:
            if entity_type == "partner_worknode":
                results[entity_type] = _sync_partner_worknode_full(sync_type, triggered_by)
            else:
                results[entity_type] = _sync_entity_incremental(
                    entity_type, sync_type, triggered_by
                )
        except Exception as e:
            # Already logged inside the helper. Continue with other entities.
            results[entity_type] = None

    return results


def _sync_entity_incremental(entity_type, sync_type, triggered_by):
    cursor = _get_cursor(entity_type)

    run = SyncRun.objects.create(
        sync_type=sync_type,
        entity_type=entity_type,
        updated_after=cursor,
        status="running",
        triggered_by=triggered_by,
    )

    try:
        if entity_type == "user":
            records = fetch_users_updated_after(cursor)
        else:
            records = fetch_partners_updated_after(cursor)

        upserted_logins = []
        upserted_partner_ids = []
        for record in records:
            obj = _upsert(entity_type, record)
            if entity_type == "user":
                upserted_logins.append({"user_login": obj.user_login, "user_name": obj.user_name})
            else:
                upserted_partner_ids.append({"partner_id": obj.partner_id, "partner_name": obj.partner_name})

        run.status = "success"
        run.records_fetched = len(records)
        run.user_logins = upserted_logins or None
        run.partner_ids = upserted_partner_ids or None
        run.completed_at = timezone.now()
        run.save()
        return run
    except Exception as e:
        run.status = "failed"
        run.error_details = str(e)
        run.completed_at = timezone.now()
        run.save()
        raise


def _sync_partner_worknode_full(sync_type, triggered_by):
    run = SyncRun.objects.create(
        sync_type=sync_type,
        entity_type="partner_worknode",
        updated_after=None,  # full sync, no cursor
        status="running",
        triggered_by=triggered_by,
    )

    try:
        records = fetch_all_partner_worknode()
        for record in records:
            _upsert_partner_worknode(record)

        run.status = "success"
        run.records_fetched = len(records)
        run.completed_at = timezone.now()
        run.save()
        return run
    except Exception as e:
        run.status = "failed"
        run.error_details = str(e)
        run.completed_at = timezone.now()
        run.save()
        raise


def _get_cursor(entity_type):
    """Return the max updated_datetime currently stored for this entity, or None for first run."""
    if entity_type == "user":
        return User.objects.aggregate(max_ts=Max("updated_datetime"))["max_ts"]
    if entity_type == "partner":
        return Partner.objects.aggregate(max_ts=Max("updated_datetime"))["max_ts"]
    return None
```

```python
def check_failure_threshold(entity_type, current_run):
    """Called after each sync run completes. Fires notification if 3 in a row failed."""
    if current_run.status != "failed":
        return

    last_three = SyncRun.objects.filter(
        entity_type=entity_type,
        sync_type="auto",
    ).order_by("-started_at")[:3]

    if len(last_three) == 3 and all(r.status == "failed" for r in last_three):
        _create_notifications_for_admins(
            notification_type="sync_failure",
            title=f"Sync failed 3 times in a row ({entity_type})",
            body=f"The last 3 automatic sync runs for {entity_type} have failed. "
                 f"Last error: {current_run.error_details}",
            metadata={"sync_run_id": current_run.sync_run_id, "entity_type": entity_type},
        )


def check_sync_silence():
    """Called hourly by heartbeat cron. Fires notification if no successful sync in 24h."""
    last_success = SyncRun.objects.filter(
        sync_type="auto",
        status="success",
    ).order_by("-completed_at").first()

    if not last_success:
        return

    hours_since = (timezone.now() - last_success.completed_at).total_seconds() / 3600

    if hours_since > 24:
        # Avoid duplicate: only fire if no sync_silent notification in last 24h
        recent_alert = Notification.objects.filter(
            notification_type="sync_silent",
            created_at__gte=timezone.now() - timedelta(hours=24),
        ).exists()

        if not recent_alert:
            _create_notifications_for_admins(
                notification_type="sync_silent",
                title="Sync has not run in 24 hours",
                body=f"The last successful sync was at {last_success.completed_at}. "
                     f"Check the cron job status on the production server.",
                metadata={"hours_since_last_success": round(hours_since, 1)},
            )


def _create_notifications_for_admins(notification_type, title, body, metadata):
    admins = User.objects.filter(
        user_role__icontains="admin",
        is_active=True, removed=False,
    )
    for admin in admins:
        Notification.objects.create(
            user_id=admin,
            notification_type=notification_type,
            title=title,
            body=body,
            metadata=metadata,
        )
```

## F-M4-9 — Partner deactivation cascade

### What it does

Today, partner deactivation is field-only: `bulk_upsert_partners` sets `Partner.is_active = not crm_partner_removed` on every sync (F-M1-2), and nothing downstream reacts to it. There is no cascade — a school that goes inactive in Hasura leaves every slot, volunteer, class, and child underneath it sitting `is_active=True` in Session-Ops forever.

F-M4-9 adds a second, independent trigger signal and a real cascade. On every partner sync (cron incremental **and** manual "Sync now" — both paths already funnel through the same `bulk_upsert_partners`), for each incoming Hasura row:

- If `crm_partner_removed = false` **and** `converted = false` **and** the partner was **both** `is_active=True` **and** `converted=True` in Session-Ops *before* this sync run — the school is treated as a real converted partner that reverted to a non-converted CRM stage without being formally removed. This is a distinct condition from F-M1-2's existing `crm_partner_removed`-driven flag flip; under the current logic alone, `removed=false` would leave (or make) the partner active. F-M4-9 overrides that outcome for this specific combination.
- When the condition fires, the school's entire operational footprint is cascade-deactivated in one transaction, and `Partner.is_active` is forced to `False` regardless of what the normal upsert logic computed.
- If the partner was **already** `is_active=False` before this sync run, nothing fires — this makes the cascade naturally idempotent across repeated sync cycles that keep reporting the same removed/converted state.
- **The previous-`converted=True` requirement is not optional — it's what distinguishes "reverted" from "never converted."** `Partner.is_active` is driven only by `crm_partner_removed` (F-M1-2), so a brand-new, never-converted lead is still created with `is_active=True` on its first sync. An earlier version of this check fired on "previously active" alone; that wrongly cascade-deactivated every never-converted lead starting on its *second* sync (nothing had changed — the row still matched `removed=false, converted=false`, and it was already "previously active" from creation), and kept re-matching forever after. Requiring previous `converted=True` too means the check only fires on a genuine converted→reverted transition. (Caught by `test_sync_is_idempotent` in `tests/features/m1/test_f_m1_2_hasura_sync.py`, which syncs an unchanged never-converted partner twice.)
- The check only applies to partners that already existed in Session-Ops before this sync. A brand-new partner seen for the first time with `removed=false, converted=false` is a normal not-yet-converted lead, not a cascade trigger — there's nothing to deactivate yet, and it was never previously converted either.
- No automatic reactivation. If a cascaded partner's Hasura state later flips back to `converted=true`, the normal upsert logic will set `Partner.is_active=True` again, but none of the cascaded child records are restored. Reversing a cascade is a manual/admin operation, confirmed permanently out of scope, not just deferred.

### Cascade order and scope

All rows are matched by the loose integer `school_id` (== `partner_id`) — none of these tables have a real Django FK to `Partner`. Only currently-active (`is_active=True, removed=False`) rows are touched, so re-running the cascade against an already-cascaded school is a no-op.

**Step 1 — volunteer/slot/section assignment layer** (bulk `.update(is_active=False, removed=True, deleted_at=now)`):
1. `SlotClassSectionVolunteer` — via `slot_class_section_id__slot_id__school_id`
2. `SlotClassSection` — via `slot_id__school_id`
3. `Slot` — direct `school_id`
4. `ClassSectionSubject` — via `class_section_id__school_id`
5. `SchoolVolunteer` — direct `school_id`
6. `ChildClassSection` — via `child_id__school_id` (the child's **bucket/section** assignment — distinct from `ChildClass` in step 3 below, the child's **grade-level** assignment)
7. `BatchChild` — direct `school_id` (added 2026-10-01)
8. `ChildProgram` — via `child_id__school_id` (added 2026-10-01)
9. `ChildSubject` — via `child_id__school_id` (added 2026-10-01)

**Step 2 — children**, per active `Child` at the school (`school_id=school_id, is_active=True, removed=False`):
1. Create a `ChildRemovalLog` row: `removed_reason="other"`, `other_details="School dropped from CRM"`, `removed_datetime=now`.
2. Deactivate the `Child` row (`is_active=False, removed=True, deleted_at=now`).

This mirrors `deactivate_child()` (`services/children/deactivate.py`) but is a bulk variant — R10 (removal reason mandatory) is satisfied by always writing `"other"` + the fixed `other_details` string, since there's no human operator to ask for a more specific reason.

**Step 3 — structural/parent layer** (bulk `.update(...)`, same soft-delete fields):
1. `ChildClass` — via `child_id__school_id`
2. `ClassSection` — direct `school_id`
3. `SchoolClass` — direct `school_id`
4. `SchoolAcademicYear` — direct `school_id`
5. `SchoolSessionDetails` — direct `school_id`
6. `SchoolHoliday` — direct `school_id` (**all** active holidays, not just future ones)

**Step 4 — the partner itself:** `Partner.is_active = False`, `deleted_at = now` (Partner has no separate `removed` field — it inherits `SoftDeleteBaseModel`, whose soft-delete is `is_active` + `deleted_at` + `deleted_by` only).

The partner upsert (`bulk_create`) and every cascade it triggers share one outer `transaction.atomic()` (2026-10-01), so a failed cascade also rolls back the partner's new `converted=false` and the next sync retries it. The cascade itself runs inside its own nested `transaction.atomic()` with the `Partner` row locked (`select_for_update()`) for the duration, so a concurrent write against the same school can't interleave. In practice this is a defense-in-depth measure — M4 decision #16 already blocks concurrent `SyncRun`s.

### Backend — service

#### `services/sync/partner_deactivation.py::cascade_deactivate_school` (NEW)

```python
from django.db import transaction
from django.utils import timezone

from sessionops.models import (
    Child, ChildClass, ChildClassSection, ChildRemovalLog, ClassSection,
    ClassSectionSubject, Partner, SchoolAcademicYear, SchoolClass,
    SchoolHoliday, SchoolSessionDetails, SchoolVolunteer, Slot,
    SlotClassSection, SlotClassSectionVolunteer,
)

# System actor for sync-triggered ChildRemovalLog rows (mandatory field, no
# human operator to attribute the removal to). Resolved during build: use
# a real existing user_id, matching M7's precedent of not inventing a bot user.
SYSTEM_SYNC_CO_ID = 485003


def cascade_deactivate_school(school_id: int, now=None) -> dict:
    """
    Cascade-deactivate every active operational record under school_id.
    Idempotent: rows already is_active=False are excluded by every filter,
    so re-running against an already-cascaded school is a no-op.
    """
    now = now or timezone.now()
    counts: dict[str, int] = {}

    with transaction.atomic():
        Partner.all_objects.select_for_update().filter(partner_id=school_id).first()

        counts["slot_class_section_volunteer"] = SlotClassSectionVolunteer.objects.filter(
            slot_class_section_id__slot_id__school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["slot_class_section"] = SlotClassSection.objects.filter(
            slot_id__school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["slot"] = Slot.objects.filter(
            school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["class_section_subject"] = ClassSectionSubject.objects.filter(
            class_section_id__school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["school_volunteer"] = SchoolVolunteer.objects.filter(
            school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["child_class_section"] = ChildClassSection.objects.filter(
            child_id__school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        active_child_ids = list(
            Child.objects.filter(school_id=school_id, is_active=True, removed=False)
            .values_list("child_id", flat=True)
        )
        ChildRemovalLog.objects.bulk_create(
            ChildRemovalLog(
                child_id_id=child_id,
                co_id=SYSTEM_SYNC_CO_ID,
                school_id=school_id,
                removed_reason="other",
                other_details="School dropped from CRM",
                removed_datetime=now,
            )
            for child_id in active_child_ids
        )
        counts["child_removal_log"] = len(active_child_ids)
        counts["child"] = Child.objects.filter(child_id__in=active_child_ids).update(
            is_active=False, removed=True, deleted_at=now
        )

        counts["child_class"] = ChildClass.objects.filter(
            child_id__school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["class_section"] = ClassSection.objects.filter(
            school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["school_class"] = SchoolClass.objects.filter(
            school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["school_academic_year"] = SchoolAcademicYear.objects.filter(
            school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["school_session_details"] = SchoolSessionDetails.objects.filter(
            school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        counts["school_holiday"] = SchoolHoliday.objects.filter(
            school_id=school_id, is_active=True, removed=False
        ).update(is_active=False, removed=True, deleted_at=now)

        Partner.all_objects.filter(partner_id=school_id).update(
            is_active=False, deleted_at=now
        )

    return counts
```

### Integration point — `services/sync/upsert.py::bulk_upsert_partners` (EXTEND)

Both live entry points (`services/sync/incremental.py::_sync_partners` for the cron path, `services/sync/trigger.py::_execute_partner_sync` for the manual "Sync now" path) already call the same shared `bulk_upsert_partners(batch_rows, now)`. Hooking the cascade check into that one function, rather than into both call sites, means neither caller needs to change:

```python
def bulk_upsert_partners(batch_rows: list[dict], now: datetime) -> tuple[int, int]:
    objects = [obj for row in batch_rows if (obj := build_partner_obj(row, now))]
    if not objects:
        return 0, 0

    batch_ids = [o.partner_id for o in objects]
    existing_ids = set(
        Partner.all_objects.filter(partner_id__in=batch_ids).values_list("partner_id", flat=True)
    )
    # F-M4-9: snapshot BEFORE the upsert overwrites is_active/converted below.
    # Both checks are required — see "previous-converted=True requirement" above.
    previously_active_ids = set(
        Partner.all_objects.filter(partner_id__in=batch_ids, is_active=True)
        .values_list("partner_id", flat=True)
    )
    previously_converted_ids = set(
        Partner.all_objects.filter(partner_id__in=batch_ids, converted=True)
        .values_list("partner_id", flat=True)
    )

    for attempt in range(2):
        try:
            Partner.all_objects.bulk_create(
                objects,
                update_conflicts=True,
                update_fields=PARTNER_UPDATE_FIELDS,
                unique_fields=["partner_id"],
            )
            created = sum(1 for o in objects if o.partner_id not in existing_ids)
            updated = len(objects) - created

            for row in batch_rows:
                partner_id = to_int(row.get("partner_id"))
                if (
                    partner_id is None
                    or partner_id not in previously_active_ids
                    or partner_id not in previously_converted_ids
                ):
                    continue
                crm_removed = bool(row.get("crm_partner_removed", False))
                converted = bool(row.get("converted", False))
                if not crm_removed and not converted:
                    cascade_deactivate_school(partner_id, now)

            return created, updated
        except OperationalError:
            if attempt == 0:
                logger.warning("bulk_upsert_partners: connection lost, reconnecting...")
                close_old_connections()
                time.sleep(2)
            else:
                raise
    return 0, 0
```

### Acceptance criteria

1. Partner with `crm_partner_removed=false, converted=false`, previously both `is_active=True` **and** `converted=True`, triggers the full cascade and ends with `Partner.is_active=False`
2. Partner already `is_active=False` before the sync run does not re-trigger the cascade (idempotent across repeated runs)
3. A partner seen for the first time (no prior row) with `removed=false, converted=false` does NOT cascade — treated as a normal new lead
4. A partner that has **never** been converted (`converted=False` since creation) does NOT cascade on any subsequent sync, even with fully unchanged data — only a genuine converted→reverted transition triggers it
5. `converted=true` (regardless of `crm_partner_removed`) never triggers the cascade
6. `crm_partner_removed=true` never triggers this cascade (that's F-M1-2's existing path)
7. All 6 step-1 tables (`slot_class_section_volunteer`, `slot_class_section`, `slot`, `class_section_subject`, `school_volunteer`, `child_class_section`) end with zero active rows for the school
8. Every previously-active `Child` at the school gets exactly one `ChildRemovalLog` row with `removed_reason="other"`, `other_details="School dropped from CRM"`
9. Every previously-active `Child` at the school ends `is_active=False`
10. All 6 step-3 tables (`child_class`, `class_section`, `school_class`, `school_academic_year`, `school_session_details`, `school_holiday`) end with zero active rows for the school
11. Records belonging to a *different* school are untouched by the cascade
12. Cascade fires identically whether triggered by the cron incremental sync or the manual "Sync now" button
13. Cascade runs inside a single transaction — a failure partway through rolls back all steps for that school
