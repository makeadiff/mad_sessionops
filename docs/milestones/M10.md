# Part 1 — Milestone Overview

## Production goal

At the end of M10, an admin can move schools from one academic year to the next in 3–4 clicks, without a developer and without code changes, and it keeps working year after year:

1. Admins maintain the **class catalog** themselves: add classes (e.g. 9th), set each class's **next class**, and switch a class **open or closed for new enrolment**.
2. Every screen, rule and export works on **the school's own active academic year**. A school that hasn't been progressed keeps working normally in its current year.
3. The admin picks converted schools. The system then **prechecks** them (blockers and warnings), **previews** exactly what will change (including optional graduation), and **runs** the progression **one school at a time, one transaction per school**, with a full log.
4. While a school is progressing it's **frozen** and hidden from COs and CHOs. A failure never leaves a school half-progressed. It stays on its old year, the reason is logged, and the admin can retry.
5. A progressed school can be **undone** until someone writes new-year data for it.

## What progression does to each table

This is the core of the milestone. "Archive" means `is_active=False, removed=False, deleted_at` untouched, which is D027's history-preserved state. Nothing is hard-deleted (R9).

| Table | Progression | Notes |
|---|---|---|
| `AcademicYear` | The target year becomes globally active and the previous one inactive, once, when the first run starts (R8) | Later runs target the already-active year |
| `SchoolAcademicYear` | Old: **archive**. New: **create** for the target year | Only for the selected **converted** schools. Active school-years of non-converted schools are archived as cleanup when a run starts |
| `SchoolClass` | Copy every active offering into the new school-year (5th → 5th). Also add any class that promoted children need and the school doesn't offer yet (e.g. 7th → 8th creates 8th) | Old rows archived. Old→new ID map logged |
| `ClassSection` (sections and mentoring circles) | For **every** active section, including empty ones: new row with the **same `section_name` and `section_display_name`**, the new school-year, and `school_class_id = NULL`, `section_code = NULL` (the decoupled M6 model) | Old rows archived **first**, because the slug-uniqueness constraint only applies to active rows. Old→new ID map logged (e.g. 5 → 100) |
| `ChildClass` | Old: archive. New: points to the new-year `SchoolClass` for the child's **next class**, or the **same class** when the class has no next class | Graduating children get no new `ChildClass` (see below) |
| `ChildClassSection` | Old: archive. New: points to the **mapped section** (5 → 100) | A child with no section stays with no section |
| `BatchChild` | Old (old school-year): archive. New: created for the new school-year | |
| `SchoolVolunteer` | Old: archive. New: created for the new school-year, for every active row | |
| `Slot`, `SlotClassSection`, `SlotClassSectionVolunteer` | **Archive only** | The CO builds the new timetable. Volunteers start the year unassigned |
| `ClassSectionSubject`, `ChildSubject` | **Archive only** (old-section rows) | New ones are created as usual when slot-classes are built |
| `SchoolSessionDetails` | **Archive only** | No new term dates. The CO sets them with the existing "Set session" flow; the MOU sign date + 60 days default is unchanged |
| `SchoolHoliday` | **Untouched** | Linked to its school-year (F-M10-4), so old-year holidays drop out of view automatically |
| `Child`, `ChildProgram`, `ChildRemovalLog`, `Class`, `Program` | Untouched | Except for graduating children |
| Inactive children | Untouched | They have no active placement. Reactivating one later places them in the new year (F-M10-2) |

**Graduation (optional, per school, chosen in the preview).** The admin can mark whole classes or individual children to graduate. Each one is deactivated in the same transaction:
- `Child.is_active=False`
- a `ChildRemovalLog` entry with the new reason **`graduated`**
- links retired exactly as `deactivate_child` does

Nobody graduates automatically. With no marks, every child either moves to the next class or stays in a class that has no next class.

## What does NOT ship in M10

Hard out-of-scope:
- **Automatic or date-triggered progression.** It's always an admin action.
- **Viewing old years.** Screens show only the school's active year; there's no year picker. Old rows are kept for records and the database only.
- **Copying the timetable, assignments or term dates forward.** They're archived and rebuilt by the CO.
- **Copying holidays into the new year.** Old holidays are kept, linked to their year, and hidden.
- **Multiple programs or subjects** (single Program and the "Foundation" subject stay as today). **Moving role names and system user IDs into config.** Both were discussed and deferred.
- **Celery or background jobs.** The browser drives the run one school per request (Celery isn't active).
- **Per-school active year as a product concept for COs.** COs never choose a year; they always work in their school's single active year.
- **Undo after new-year writes.**

## Key architectural decisions

**1. Year scope comes from the school, not the global flag.** Every year-bound read filters on the **school's own active `SchoolAcademicYear`** (`school_academic_year_id__is_active=True, removed=False`). A new DB constraint (F-M10-2) guarantees each school has exactly one. The global `AcademicYear.is_active` stays the single "current year" (R8). It's the year new schools start in and the year progression moves schools into.

This replaces the M9 `active_year_slot_q`, which filtered on the global year. That was correct while only one year existed, but after the flip it would blank out every school that hadn't been progressed yet.

**2. Flip first, then progress schools.** Starting the first run flips the global year in one transaction and archives non-converted schools' active school-years. Schools that haven't been progressed keep working in their old year (decision 1) until an admin progresses them.

**3. One transaction per school.** Each school's execution either commits completely or rolls back completely. There's never a half-progressed school. A failure leaves that school on its old year, frozen, with the error logged, ready to retry. A run with 68 schools is 68 independent commits.

**4. The browser drives the run.** The Run step calls `execute` for one school at a time and shows live progress. There's no long HTTP request (the frontend timeout is 30 s) and no Celery.
- If the admin closes the tab, the run stays `in_progress`, and schools not yet executed stay `queued` (frozen).
- The Runs tab can resume it.

**5. Freeze means "no user writes, hidden from COs and CHOs".**
- **When:** from Start until a school's own execution finishes, successfully or not. Failed schools stay frozen until they're retried or released.
- **COs and CHOs:** a frozen school is hidden from them.
- **Admins:** they see it with a "Progressing" badge and can't edit it through normal screens.
- **System writes are not blocked.** Realtime sync and partner sync still run: execution copies whatever is active at that moment, and it locks the school's `SchoolAcademicYear` row (`select_for_update`) so a sync waits a few seconds.

**6. Every created and archived row is logged.** `ProgressionRowLog` records the table, row id, action (`created` / `archived`) and the old id (for maps). That log is used for the audit, the counts and undo.

**7. The class catalog is data, not code.** It gains `sequence`, `next_class_id` and `open_for_enrolment`, which replaces `BLOCKED_NEW_CLASS_CODES = {"8"}`. Progression uses `next_class_id` only. It never infers "next" from the name or code, and there's no hard-coded final class.

**8. Precheck is authoritative, and execution re-checks.** Blockers are evaluated again inside each school's transaction, so data that changed between the preview and the run can't slip through.

## F-M10-1 — Class catalog admin

**What:** Admins manage the class catalog from a new **Admin → Classes** page:
- add a class (e.g. 9th)
- set its display order
- set its **next class**
- toggle **open for new enrolment / editing**

This replaces the hard-coded `BLOCKED_NEW_CLASS_CODES`, and it's the only input progression uses to decide where children go.

**Who uses it:** Admin (ADMIN_ROLES: Function Lead, Project Lead, Project Associate).

**Business rules enforced:**
- **Next class:**
  - It must be a different, **active** class.
  - Chains can't form a cycle (5→6→5 is rejected).
  - `null` means "children stay in this class".
- **Classes closed to enrolment** (`open_for_enrolment=False`) can't be used to enroll a child, move a child into it by editing, or add it to a school. **Progression and reactivation to the child's prior class** are the only ways in. This is the current 8th behaviour, now driven by data.
- **Deactivating a class:**
  - It's blocked while any active `SchoolClass` uses it.
  - It's blocked while another class's `next_class_id` points to it.
- **`class_code` is still unique.** `sequence` controls display order everywhere classes are listed (numeric, so 10 sorts after 9).

**Backend scope:**
- **Model:** `Class` gets `sequence` (IntegerField), `next_class_id` (FK self, null, PROTECT, `db_column="next_class_id"`), and `open_for_enrolment` (bool, default True).
- **Data migration:**
  - sequence = int(class_code) when numeric, otherwise 1000
  - next_class: 5→6, 6→7, 7→8, 8→null
  - `open_for_enrolment=False` for "8", True for the rest
- **Endpoints** (admin only, via `user_has_admin_access`, same pattern as `admin_sync_api._require_admin`):
  - `GET /api/admin/classes/`: all classes, including inactive, ordered by `sequence`
  - `POST /api/admin/classes/`: `{class_code, class_name, sequence, next_class_id?, open_for_enrolment}`, using the single active Program as today
  - `PATCH /api/admin/classes/{class_id}/`: any of the fields above, plus `is_active`
- **Services (`services/catalog/`):**
  - `list_catalog`, `create_class`, `update_class`
  - `validate_next_class`: rejects itself, inactive classes and cycles
  - `assert_class_open_for_enrolment(class_obj, *, allow_prior=False)`, which replaces `assert_class_not_blocked_for_assignment`
- **Callers switched:**
  - `add_class_to_school`, `enroll`, child `edit` and `reactivate`
  - the catalog endpoint `GET /api/classes/`, which lists only open classes, ordered by `sequence` (it used to exclude "8" by hard code)
- **Removed:** `BLOCKED_NEW_CLASS_CODES`.

**Frontend scope:**
- New route `app/admin/classes/page.tsx` → `components/admin/ClassCatalogPage.tsx`.
  - **Table:** Order · Class · Code · Next class · Open for enrolment (switch) · Status · Edit.
  - **Add / Edit:** a side drawer, with the Next class as a dropdown of active classes plus "None — children stay".
- An Admin nav item "Classes", admin-only, using the same role check as the Admin page.
- `lib/api/services/catalog.service.ts`.

**Acceptance criteria:**
- [ ] After the migration the catalog is 5th(1)→6th, 6th(2)→7th, 7th(3)→8th, 8th(4)→none. 8th is closed; the others are open.
- [ ] An admin can add "9th" and set 8th → 9th. Progression then moves 8th children to 9th (verified in F-M10-7).
- [ ] Setting next class to itself, to an inactive class, or in a way that creates a cycle returns 400 with a clear message.
- [ ] Enrolling into, editing into, or adding to a school a class that's closed to enrolment returns 400. Reactivating a child into their prior class still works.
- [ ] `GET /api/classes/` lists open, active classes ordered by `sequence`. `BLOCKED_NEW_CLASS_CODES` no longer exists.
- [ ] A CO or CHO calling the admin endpoints gets 403.
- [ ] Deactivating a class in use, or one that's the next class of another class, returns 409.

**Test scenarios:**
- Happy path: add 9th, point 8th at it, and the catalog lists 9th.
- Edge case: the class chain 5→6→7 when 7's next class is set to 5 (a cycle) is rejected.
- Edge case: a class code "10" sorts after "9" by sequence.
- Error case: a CO calls POST → 403.

## F-M10-2 — School-year integrity

**What:** Guarantees that every school has **exactly one** active `SchoolAcademicYear` and that every write lands in it. Removes the crash paths that assume this without enforcing it.

**Who uses it:** Everyone (indirectly).

**Business rules enforced:**
- **R8:** one globally active academic year.
- **One active school-year per school**, enforced by a new DB constraint and documented as a new rule in BUSINESS_RULES.md.
- **Schools that join mid-year** get a school-year for the **global active year** on their first write (unchanged behaviour of `get_or_create_school_academic_year`).

**Backend scope:**
- **Migration:** a partial `UniqueConstraint(fields=["school_id"], condition=Q(is_active=True, removed=False), name="uniq_active_say_per_school")`.
  - It runs **after** a precheck migration step that fails loudly, listing the offending schools, if any duplicates exist. No silent fixes.
- **Services:**
  - `services/academic_year/queries.py::get_school_academic_year(school_id) -> SchoolAcademicYear | None`: the school's single active row.
  - `get_or_create_school_academic_year` uses it.
  - `enroll` and `reactivate` use `get_or_create_school_academic_year` instead of `.get(...)`. This removes the `MultipleObjectsReturned` / 409 paths.
- **`reactivate`:**
  - The "restore prior class" check compares **catalog `class_id`** instead of `school_class_id`. The prior `SchoolClass` belongs to an archived year after progression.
  - The child is placed in the **current** school-year's `SchoolClass` for that catalog class.

**Frontend scope:** none.

**Acceptance criteria:**
- [ ] The migration applies on dev (0 duplicates on 2026-09-28). With a seeded duplicate, it fails and names the school.
- [ ] Creating a second active school-year for a school raises an `IntegrityError` at the DB.
- [ ] Enroll and reactivate work for a school with no school-year yet: one is created for the global year.
- [ ] Reactivating a child whose last class was 8th in an archived year places them in the current year's 8th, even though 8th is closed to enrolment.

**Test scenarios:**
- Happy path: a new school's first enrolment creates its school-year.
- Edge case: reactivation across a year boundary.
- Error case: a duplicate active school-year blocks the migration.

## F-M10-3 — Year-scoped reads by the school's own active year

**What:** Every read of year-bound data filters on the school's own active school-year. After progression, old-year rows disappear from every screen, rule and export, and schools that haven't been progressed are unaffected.

**Who uses it:** CO, CHO, Admin (every school screen and export).

**Business rules enforced:**
- **R1, R2, R6, R7:** evaluated only against the school's active year.
- **Bucket and section name uniqueness:** per school within the active year. An archived "Group A" doesn't block a new "Group A".
- **M9 decision 9** is kept: "only the active year is visible", reinterpreted as the school's active year.

**Backend scope:**
- **Replace `active_year_slot_q`** with `current_year_q(prefix)`: `Q(<prefix>school_academic_year_id__is_active=True, <prefix>school_academic_year_id__removed=False)`.
  - It's valid for single- and multi-school queries, because each school has exactly one active row (F-M10-2).
- **Apply it to:**

| Area | Read paths |
|---|---|
| Classes and buckets | `list_classes_for_school`; `list_buckets_for_school`; bucket and section name pre-checks in `create_bucket` / `edit_bucket`; the bucket lookups in `enroll`, `edit`, `bucket_children` |
| Slots | `list_slots`; the R7 overlap checks in `create_slot` / `edit_slot`; `get_school_schedule` |
| Volunteers | `list_school_volunteers` counts; R6 (`check_r6_volunteer_single_assignment`) |
| Term dates | `get_active_session` (now the school's active school-year, not the global year) and the holiday create window that depends on it |
| Counts | `get_school_stats` (classes, assignments), `schools_summary_rows` (buckets, slots, sessions) |
| Exports | M9 volunteers, timetable and gaps exports |

- **Children lists** need no year filter. Placement comes from active `ChildClass` / `ChildClassSection` rows, and progression archives the old ones.
- **Guards:** `soft_delete_section` and `soft_delete_school_class` count only active-year dependants.

**Frontend scope:** none. The year label already comes from the school's own school-year.

**Acceptance criteria:**
- [ ] With an archived old-year school-year holding classes, buckets, slots, assignments and a session, **none** of them appear in any tab, count or export for that school. A school on the old year still sees all of its own data.
- [ ] An archived "Group A" doesn't block creating "Group A" in the new year.
- [ ] R6: a volunteer whose only assignment is in an archived year can be assigned.
- [ ] R7: an archived slot doesn't cause an overlap conflict.
- [ ] All existing M3/M6/M9 tests pass, updated only where they relied on the global year. The M9 `test_m9_active_year_filter.py` cases are rewritten to use the school's own year and still cover every surface.
- [ ] No read path queries `AcademicYear.is_active` for scoping, apart from the global label and the 404 guards (checked with grep in review).

**Test scenarios:**
- Happy path: after progression (fixture), each tab shows only new-year data.
- Edge case: two schools, one progressed and one not, give correct results for each in the same cross-school export.
- Error case: none (read-only).

## F-M10-4 — Holidays linked to the school-year

**What:** Holidays get a year link so they belong to one school-year, the same as term dates. Old holidays aren't archived; the year scope hides them.

**Who uses it:** CO (Calendar tab).

**Business rules enforced:** holiday dates must fall within the school's active session (unchanged). The holiday's school-year is the school's active one.

**Backend scope:**
- **Migration:** `SchoolHoliday.school_academic_year_id` FK (null, PROTECT, `db_column="school_academic_year_id"`).
- **Data migration:** backfill each active and archived holiday to the school's active school-year. Use `.using(schema_editor.connection.alias)`, as `check_migration_db_alias.py` requires.
- **Services:** `create_holiday` sets the school-year. `list_holidays` filters with `current_year_q()`.

**Frontend scope:** none.

**Acceptance criteria:**
- [ ] After the migration, every existing holiday has its school's active school-year (1 in dev).
- [ ] After a school is progressed, its old holidays no longer appear, and new holidays attach to the new school-year.
- [ ] Holiday create, edit and delete behave as before for schools that haven't been progressed.

**Test scenarios:**
- Happy path: a holiday created now is linked to the active school-year.
- Edge case: the backfill leaves a holiday null when the school has no school-year, and it's still visible (a documented fallback, shown while null).
- Error case: none new.

## F-M10-5 — Progression run model, row log and school freeze

**What:** Adds the records that make a run auditable and resumable, and the freeze that keeps users out of a school while it progresses.

**Who uses it:** Admin (directly). CO and CHO (they experience the freeze).

**Business rules enforced:**
- A school can be in at most **one** unfinished `SchoolProgression` at a time.
- **Frozen school** (`queued`, `running` or `failed`):
  - Every user write through the API returns 409 `school_progressing`.
  - It's excluded from `schools_visible_to` for non-admins.
  - Admins still see it, read-only, with a badge.
- **System writes aren't blocked.** Realtime sync and partner sync are covered by the row lock in F-M10-7.

**Backend scope:**
- **Models (`models/progression.py`)**. None of these have soft-delete columns; they're append and update-only audit records, like `ExportLog`.
  - **`ProgressionRun`:**
    - `run_id`, `from_academic_year_id`, `to_academic_year_id` (FK AcademicYear)
    - `started_by` (FK User), `started_at`, `finished_at`
    - `status`: `in_progress` / `completed` / `completed_with_failures`
  - **`SchoolProgression`:**
    - `run_id` (FK), `school_id`
    - `from_school_academic_year_id`, `to_school_academic_year_id` (null until executed)
    - `status`: `queued` / `running` / `completed` / `failed` / `undone` / `released`
    - `graduate_class_ids` (JSON), `graduate_child_ids` (JSON)
    - `counts` (JSON), `warnings` (JSON), `error` (text)
    - `started_at`, `finished_at`, `undone_at`, `undone_by`
    - Index on `(school_id, status)`.
  - **`ProgressionRowLog`:**
    - `school_progression_id` (FK)
    - `table` (e.g. `class_section`), `row_id`, `action` (`created` / `archived`), `source_row_id` (the old id, for created rows)
    - Index on `(school_progression_id, table)`.
- **Freeze:**
  - **`services/progression/freeze.py::is_school_frozen(school_id)`.**
  - **`assert_school_writable(school_id)`:**
    - It's called from `can_modify_school` / `get_school_or_403` write paths, from one central place in `services/rbac/scope.py`.
    - It raises `ConflictError(code="school_progressing")`.
  - **`schools_visible_to`** excludes frozen schools for non-admin scope.
- **Release:** `POST /api/admin/progression/runs/{run_id}/schools/{school_id}/release/` releases a `failed` school without retrying, which unfreezes it on its old year (status `released`).

**Frontend scope:**
- **School list (CO/CHO):** a dismissible banner when some of the user's schools are hidden, e.g. "N of your schools are being moved to 2027-2028. They'll be back shortly." The count comes from a new field `progressing_count` on `GET /api/schools/`.
- **Admin views of a frozen school:** a "Progressing" chip, and write buttons disabled via the existing `useUserCan`. `GET /auth/me/permissions` returns `canModify=false` for frozen schools.

**Acceptance criteria:**
- [ ] For a `queued`, `running` or `failed` school:
  - Every write endpoint (children, classes, buckets, slots, slot-classes, sessions, holidays) returns 409 `school_progressing`.
  - A CO's and CHO's school list and detail don't show it (detail returns 404, list omits it and increments `progressing_count`).
  - An admin sees it, and `canModify=false`.
- [ ] `completed`, `undone` or `released` schools behave normally.
- [ ] A second unfinished `SchoolProgression` for the same school is rejected.
- [ ] Realtime-sync user updates for a frozen school still succeed.

**Test scenarios:**
- Happy path: a queued school is hidden from its CO and visible to an admin.
- Edge case: a failed school stays frozen until it's retried or released.
- Error case: a CO POSTs a child to a frozen school → 409.

## F-M10-6 — Precheck and preview, including graduation

**What:** The read-only analysis before a run. **Precheck** classifies each selected school as ready, warning or blocked. **Preview** shows exactly what will be created, moved and archived, and lets the admin mark classes or children to graduate.

**Who uses it:** Admin.

**Business rules enforced:**

**Eligible schools:** `converted=True`, not frozen, with an active school-year, and the year after it already exists (otherwise `NO_NEXT_YEAR`). Revised 2026-10-05.

**Blockers** (that school can't be selected for Start):

| Code | Condition |
|---|---|
| `NOT_CONVERTED` | The school isn't converted |
| `ALREADY_ON_TARGET` | The school's active year is already the target |
| `NO_ACTIVE_SCHOOL_YEAR` | The school has no active school-year, or more than one |
| `CHILD_CLASS_CONFLICT` | An active child has 0 or more than 1 active `ChildClass` |
| `CHILD_SECTION_CONFLICT` | An active child has more than 1 active `ChildClassSection` |
| `NEXT_CLASS_INACTIVE` | A class in use points to a next class that's inactive |
| `ALREADY_IN_RUN` | The school has an unfinished progression |
| `TARGET_NOT_LATER` | The target year's label isn't later than the school's current year |

**Warnings** (shown in the drawer; the school can still run):

| Code | Condition |
|---|---|
| `NO_NEXT_CLASS` | N children are in a class with no next class, so they'll stay in that class |
| `CHILD_NO_SECTION` | N children have no section, so they'll stay without one |
| `CLASS_CLOSED_TARGET` | Children will land in a class closed to enrolment (allowed for progression) |
| `LEGACY_NO_SCHOOL_YEAR` | Rows with no school-year exist (e.g. 1 `SchoolVolunteer` in dev). They're archived as part of the old year |
| `ACTIVE_TIMETABLE` | N slots, slot-classes and assignments will be archived; the CO must rebuild |
| `ACTIVE_SESSION` | Term dates will be archived; the CO must set new ones |

**Preview counts per school:**
- school classes copied and school classes added (with class names)
- sections copied
- children moving, per old class → new class (e.g. 5th → 6th: 40)
- children staying (no next class)
- children graduating
- volunteers carried over
- rows archived per table

**Graduation marks:**
- Admins can select whole classes (`graduate_class_ids`) and individual children (`graduate_child_ids`).
- The preview counts update with the marks.
- A marked child who is also in a marked class is counted once.

**Backend scope:**
- **Endpoints (admin only):**
  - `GET /api/admin/progression/eligible-schools/?target_year_id=`: converted schools, each with its current year and eligibility.
  - `POST /api/admin/progression/precheck/`: `{target_year_id, school_ids}` → `[{school_id, status, blockers[], warnings[]}]`.
  - `POST /api/admin/progression/preview/`: `{target_year_id, schools: [{school_id, graduate_class_ids, graduate_child_ids}]}` → per-school counts and class breakdown.
  - `GET /api/admin/progression/preview/{school_id}/children/?class_id=`: that school's active children, for picking individuals to graduate. Paginated, so large schools stay usable in the drawer.
- **Services:** `services/progression/precheck.py`, `services/progression/preview.py`. Both are read-only, use a fixed number of queries per school, and share their mapping logic with execution so the preview can never disagree with the run.
- **Model:** `REMOVED_REASONS` gains `("graduated", "Graduated")`. It isn't added to the CO Deactivate dialog's `DeactivateIn` (user decision: graduation happens only in the progression preview).

**Frontend scope:** the Precheck and Preview steps of the wizard (F-M10-9).

**Acceptance criteria:**
- [ ] Each blocker and each warning is detected for a school that has it, and not for one that doesn't.
- [ ] Preview counts for a fixture school match exactly the rows that F-M10-7 execution then creates and archives. This is a shared test, so a count mismatch fails the build.
- [ ] Marking 8th to graduate turns the "8th stays" count into "8th graduates". Also marking one 8th child individually doesn't double-count.
- [ ] Precheck and preview make no writes (asserted: row counts unchanged).
- [ ] Query count per school is constant as the number of children grows.

**Test scenarios:**
- Happy path: a clean school is ready, and the preview shows the 5th→6th, 6th→7th and 7th→8th moves, with 8th staying.
- Edge case: after 9th is added and 8th→9th is set, the preview shows 8th → 9th and adds a 9th `SchoolClass`.
- Edge case: a school with a child who has two active classes is blocked with `CHILD_CLASS_CONFLICT`.
- Error case: a target year that isn't later than the current one gives `TARGET_NOT_LATER` for every school.

## F-M10-7 — Start run and execute per school

**What:** **Start** creates the run, flips the global year (first run only), archives non-converted schools' school-years, and freezes the selected schools. **Execute** progresses one school in one transaction, as the table in Part 1 describes.

**Who uses it:** Admin.

**Business rules enforced:**
- **Start:**
  - Rejected if any selected school is blocked (re-checked).
  - Target year: if it isn't active, it must be the only inactive year later than the current active one. Start activates it and deactivates the current one in one transaction (R8).
  - If the target year is already active (later runs), no flip happens.
  - Archives every active `SchoolAcademicYear` of `converted=False` schools (logged on the run), in the same transaction.
- **Execute:**
  - Locks the school's active `SchoolAcademicYear` (`select_for_update`).
  - Re-runs the blockers. If any are found, the school becomes `failed` with those blockers and nothing is written.
  - Then performs, in order:
    1. Create the new school-year; archive the old one.
    2. SchoolClass: copy active offerings, and add the classes that the next-class rules require.
    3. ClassSection: archive the old rows, then create copies (same name and display name, `school_class_id=NULL`, new school-year) and build the ID map.
    4. For each active child:
       - If marked to graduate: run the deactivate routine with reason `graduated`.
       - Otherwise: archive the old `ChildClass`, `ChildClassSection` and `BatchChild`, then create new ones pointing to the next-class `SchoolClass` (or the same class) and the mapped section.
    5. SchoolVolunteer: copy active rows to the new school-year and archive the old ones.
    6. Archive the old year's Slot, SlotClassSection, SlotClassSectionVolunteer, ClassSectionSubject and ChildSubject rows, and the SchoolSessionDetails.
    7. Write every created and archived row to `ProgressionRowLog`, and store the counts.
  - Any exception rolls back the whole school. Its `SchoolProgression` is then set to `failed` with the error, in a separate transaction.
  - Retrying a failed school runs execute again from scratch.
  - Rows are created with `created_by` = the admin who started the run.
  - The run's `status` moves to `completed` or `completed_with_failures` once no school is `queued` or `running`.

**Backend scope:**
- **Endpoints (admin only):**
  - `POST /api/admin/progression/runs/`: `{target_year_id, schools: [{school_id, graduate_class_ids, graduate_child_ids}]}` → the run, with schools `queued`.
  - `POST /api/admin/progression/runs/{run_id}/schools/{school_id}/execute/` → the school's result (status, counts, error). This is idempotent: executing a `completed` school returns it unchanged.
  - `GET /api/admin/progression/runs/`, `GET /api/admin/progression/runs/{run_id}/`, `GET /api/admin/progression/runs/{run_id}/schools/{school_id}/` (with the row-log summary).
- **Services:** `services/progression/start.py`, `services/progression/execute.py`. Execute reuses the shared mapping from F-M10-6 and the existing deactivate logic, refactored so it can be called with a reason and inside an outer transaction.
- **Migrations** use `.using(schema_editor.connection.alias)` rules where applicable.

**Frontend scope:** the Run step (F-M10-9). It calls execute for each queued school in turn and shows live status.

**Acceptance criteria:**
- [ ] After executing a fixture school with classes 5th–8th, sections, children in every class, volunteers, slots, assignments, a session and a holiday:
  - Every row in the Part 1 table is created or archived exactly as specified.
  - Counts equal the preview.
  - Children are in the next class with their mapped section IDs (old section id 5 → new id 100 in the child's new `ChildClassSection`).
  - 8th children stay in 8th unless they were marked to graduate.
- [ ] Section copies keep `section_name` and `section_display_name`, have `school_class_id=NULL`, and link to the new school-year. Empty sections are copied too.
- [ ] Graduated children are inactive, with a `ChildRemovalLog` reason `graduated`, and are excluded from active counts.
- [ ] An exception injected at step 5 leaves the school **exactly** as it was before execute (asserted on every table). The school is `failed` with the error, still frozen, and a retry succeeds.
- [ ] Start flips the global year once. A second run targeting the active year doesn't flip again. Start with a blocked school is rejected.
- [ ] Non-converted schools' active school-years are archived at Start.
- [ ] A realtime-sync `SchoolVolunteer` write that arrives during execute waits on the lock and ends up on the new school-year.
- [ ] Executing 68 schools one request at a time works within the frontend 30 s timeout per request, measured on the prod-data copy.

**Test scenarios:**
- Happy path: the full fixture school progresses correctly.
- Edge case: 8th→9th configured, so the 8th children move to a newly added 9th `SchoolClass`.
- Edge case: a child with no section stays with no section. An empty section is still copied.
- Edge case: after progression, a school that hasn't been progressed is completely unchanged.
- Error case: data changes after the preview so that a blocker appears; execute marks the school failed and writes nothing.

## F-M10-8 — Per-school undo

**What:** Reverses a `completed` school progression, provided nobody has written new-year data for that school since it completed.

**Who uses it:** Admin.

**Business rules enforced:**
- **Undo is allowed only when** the school is `completed` **and** the school has **no new-year writes**. That means:
  - no row that refers to the new school-year, or to a row the progression created, exists outside the progression's own row log, and
  - no logged created row has `updated_at` later than `finished_at`.
- **Undo runs in one transaction, driven by the row log:**
  - created rows become `removed=True` (soft-deleted as mistakes)
  - archived rows get `is_active=True` again
  - the old school-year is restored as the school's active year, and the new one becomes `removed=True`
  - graduated children are reactivated and their `graduated` removal log retired, following the `reactivate_child` pattern
  - status becomes `undone`
- **After undo,** the school is on its old year and eligible for another run.
- **The global year is never flipped back** by undo, even if every school is undone.

**Backend scope:**
- **Endpoint:** `POST /api/admin/progression/runs/{run_id}/schools/{school_id}/undo/`. It's admin only, returns 409 `undo_not_allowed` with the reason when ineligible.
- **Service:** `services/progression/undo.py::undo_school(school_progression, user)` and `can_undo(school_progression) -> (bool, reason)`. The run detail response includes `can_undo` per school.

**Frontend scope:** an Undo button in the school drawer on the Runs tab. It's disabled, with the reason, when not allowed, and asks for confirmation.

**Acceptance criteria:**
- [ ] Undo right after a completed execute restores **every** table to its exact pre-execute state (asserted row by row against a snapshot), apart from audit timestamps.
- [ ] After a CO creates a slot or bucket, enrolls a child, or sets term dates in the new year, `can_undo` is false and undo returns 409.
- [ ] An undone school can be progressed again in a new run and ends in the same state as the first execute.
- [ ] Graduated children are active again after undo.

**Test scenarios:**
- Happy path: execute, then undo, then compare against the snapshot.
- Edge case: undo after the global flip leaves the school on the old year, while other progressed schools stay on the new year.
- Error case: a new-year write blocks undo.

## F-M10-9 — Admin Year Progression screens

**What:** A new **Admin → Year Progression** page. It has two tabs, **New run** and **Runs**. Each job gets its own screen, with details in side drawers, so no page gets cluttered.

**Who uses it:** Admin.

**Layout (agreed 2026-09-28):**

```
Admin › Year Progression        [ New run | Runs ]

  ① Schools ─ ② Precheck ─ ③ Preview ─ ④ Run
  ──────────────────────────────────────────
  Step ② Precheck      2026-27 → 2027-28

  [search]            58 ready · 6 warn · 4 blocked
  ┌────────────────────────────────────┐
  │ School            Status     Issues  │
  │ Govt HS Shaikpet  ✔ Ready      –   › │
  │ MPS Jubilee Hills ⚠ Warning    2   › │
  │ ZPHS Kondapur     ✖ Blocked    1   › │
  └────────────────────────────────────┘
                 click › opens details drawer
                              [ Back ]  [ Next ]
```

**The four wizard steps, one screen each:**
1. **Schools.** Choose the target year from the inactive years later than the current one, or the active year once it has flipped. Then the converted, eligible schools, with search and "select all". Ineligible ones are greyed out, with the reason.
2. **Precheck.** A summary line (ready · warning · blocked) and one row per school. The drawer lists that school's blockers and warnings. Blocked schools are deselected automatically, and Next is disabled while a blocked school is selected.
3. **Preview.** One row per school with its counts. The drawer shows the class moves (old → new) and the graduation controls: whole-class checkboxes, plus a searchable child picker using the paginated endpoint. Counts refresh when marks change.
4. **Run.** A confirmation dialog that names the target year and warns that timetables and term dates will be archived. Then a live progress list (queued → running → done / failed), with the error in the drawer. Failed schools offer **Retry** and **Release**.

**Runs tab:**
- A list of runs: date, admin, from → to, and school counts by status.
- Opening a run shows its schools. Each school's drawer has counts, the row-log summary and the undo state.
- **Resume** continues any `queued` schools left behind when a tab was closed.

**Other screens:**
- **Admin → Academic Years (existing):** adds only a "Next" badge on the inactive year that would become the target. There's no progression action on this page.
- **Admin → Classes:** from F-M10-1.
- **CO/CHO:** the banner from F-M10-5. Nothing else.

**Frontend scope:**
- `app/admin/progression/page.tsx` → `components/admin/progression/` with these components:
  - `ProgressionPage`
  - `ProgressionWizard`
  - `StepSchools`, `StepPrecheck`, `StepPreview`, `StepRun`

- `lib/api/services/progression.service.ts`.
- An Admin nav item, admin-only, using the existing role check.
- MUI subpath imports and theme tokens (frontend CLAUDE.md).

**Acceptance criteria:**
- [ ] The whole flow can be completed in four steps. Blocked schools can't be run. The live list reaches done or failed for every school.
- [ ] Closing the tab mid-run and reopening Runs shows the run `in_progress`, and Resume finishes it.
- [ ] Undo is enabled or disabled per `can_undo`, and shows the reason when disabled.
- [ ] Non-admins don't see the nav item. The route redirects them to `/schools`, the same as `/admin`.
- [ ] Vitest covers:
  - step navigation and gating (Next disabled with blocked schools selected)
  - drawer contents
  - graduation marks sent in the Start payload
  - the Run step calling execute sequentially and handling a failure
  - Runs tab resume and undo states

**Test scenarios:**
- Happy path: select 3 schools, precheck (all ready), preview, run → 3 done.
- Edge case: 1 school fails during the run; Retry succeeds.
- Error case: the network drops during the run; the school stays queued, and Resume completes it.

## Resolved decisions (2026-09-28)

| # | Question | Decision |
|---|---|---|
| 1 | When do COs set up the new year? | After their school is progressed. Until then they keep their current year |
| 2 | Which schools progress? | Converted schools, **selected by the admin**. Non-converted schools' active school-years are archived as cleanup. Schools that join mid-year get the global active year automatically |
| 3 | Active years per school | Exactly one (DB constraint) |
| 4 | Viewing old years | No. Only the active year is shown |
| 5 | What moves and what's archived | The table in Part 1 (SchoolClass, ClassSection, ChildClass, ChildClassSection, BatchChild and SchoolVolunteer move; the timetable, subjects, ChildSubject and session are archived; holidays stay, linked to their year) |
| 6 | Section copies | Same name, new school-year, **no class link**, children remapped to the new section id |
| 7 | Final class | None fixed. The admin sets **next class** per class; no next class means children stay. Optional graduation with reason "graduated" |
| 8 | Class enrolment | Admin toggle "open for new enrolment / editing" per class, replacing the hard-coded 8th block |
| 9 | Default term dates | None. Old sessions are archived; the CO sets new ones (MOU sign date + 60 days default unchanged) |
| 10 | Year scope | **The school's own active year**, not the global flag |
| 11 | When the global year flips | At the first Start; schools progress afterwards |
| 12 | Freeze | Selected schools are frozen from Start until their execution finishes, hidden from COs and CHOs. System syncs aren't blocked |
| 13 | Milestone | New M10. F-M5-6 and F-M5-7 moved out of M5 |
| 14 | Undo | Per school, until the first new-year write |

## Rollback plan

- **Code rollback before any run:** F-M10-1 to F-M10-4 are additive.
  - Reverting the code leaves the new catalog columns, the constraint and the holiday FK in place, all harmless.
  - The catalog migration is reversible. The constraint can be dropped with the reverse migration.
- **After runs:**
  - Undo each progressed school (F-M10-8) while it's still eligible.
